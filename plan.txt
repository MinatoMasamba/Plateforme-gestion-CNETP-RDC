# Plan — Confirmation obligatoire de l'email par code avant authentification (utilisateur public)

## Contexte

On vient d'ajouter un système de code de confirmation par email pour les utilisateurs simples/publics (`register_public`). Actuellement le flux est incomplet et **non sécurisé** :

- `register_public` crée le compte **et renvoie immédiatement des tokens JWT** → l'utilisateur est authentifié sans avoir confirmé son email.
- `login` ne vérifie pas `email_confirmed` → un compte non confirmé peut se connecter normalement.
- `confirm_email_code` confirme l'email mais ne renvoie pas de session/tokens → Flutter n'a aucun moyen propre de "passer à l'accueil" juste après confirmation.

Le scénario voulu par l'utilisateur (à respecter intégralement) :
1. Après `register_public`, Flutter affiche la page de saisie du code — **aucune authentification n'est délivrée à ce stade**.
2. Flutter renvoie le code au serveur ; le serveur vérifie qu'il s'agit bien du code qu'il a réellement envoyé.
3. Si le code est correct → le serveur confirme l'email **et authentifie** l'utilisateur (tokens + infos) → Flutter peut aller à l'accueil.
4. Si le code est faux/expiré → message d'erreur clair ; l'utilisateur peut demander un nouveau code, **ce qui annule l'ancien** (déjà géré par `EmailConfirmationCode.create_for_user`, qui supprime les codes non utilisés existants).
5. Si un utilisateur non confirmé tente de se `login`, le serveur **refuse** l'authentification, renvoie une indication explicite ("email non confirmé") permettant à Flutter de rediriger vers la page de confirmation, et **renvoie automatiquement un nouveau code**.
6. **Jamais d'authentification sans confirmation du code.**

## Fichiers concernés

- [api/v1/mobile/views.py](api/v1/mobile/views.py) — actions `register_public`, `login`, `confirm_email_code` du `MobileAuthViewSet`
- [api/v1/mobile/serializers.py](api/v1/mobile/serializers.py) — `PublicUserRegistrationSerializer`, `MobileLoginSerializer`, `EmailConfirmationCodeSerializer`

## Modifications détaillées

### 1. `register_public` ([views.py:39-52](api/v1/mobile/views.py#L39-L52)) — ne plus authentifier à l'inscription

Supprimer la génération de `RefreshToken.for_user(user)` et les champs `access`/`refresh` de la réponse. La réponse devient une simple confirmation que le compte est créé et qu'un code a été envoyé, avec de quoi identifier le compte côté Flutter pour la page de confirmation :

```python
return Response({
    'user': MobileUserDetailSerializer(user).data,
    'email': user.email,
    'requires_email_confirmation': True,
    'message': "Inscription réussie. Un code de confirmation vous a été envoyé par email."
}, status=status.HTTP_201_CREATED)
```

(`PublicUserRegistrationSerializer.create` continue d'envoyer le code via `send_email_confirmation_code` / repli `_send_email_confirmation_code_now`, déjà en place.)

### 2. `login` ([views.py:88-123](api/v1/mobile/views.py#L88-L123) + `MobileLoginSerializer.validate`) — bloquer les comptes non confirmés

Le `MobileLoginSerializer.validate` valide déjà email + mot de passe + `is_active`, et place `user` dans `validated_data`. La génération des tokens et de la session se fait ensuite **dans la vue**.

Ajouter, juste après `user = serializer.validated_data['user']` et **avant** la génération des tokens / création de session :

```python
if not user.email_confirmed:
    try:
        send_email_confirmation_code.delay(user.id)
    except Exception:
        _send_email_confirmation_code_now(user.id)

    return Response({
        'error_code': 'EMAIL_NOT_CONFIRMED',
        'message': "Votre email n'est pas confirmé. Un nouveau code de confirmation vous a été envoyé.",
        'email': user.email,
    }, status=status.HTTP_403_FORBIDDEN)
```

Cela donne à Flutter un signal explicite (`error_code`) pour rediriger vers la page de confirmation au lieu d'un message d'erreur générique, et déclenche automatiquement l'envoi d'un nouveau code (réutilise `send_email_confirmation_code` / `_send_email_confirmation_code_now`, déjà importés dans `views.py`).

Aucun token n'est émis, aucune `MobileSession` n'est créée pour un compte non confirmé : "jamais d'authentification sans confirmation".

### 3. `confirm_email_code` ([views.py](api/v1/mobile/views.py) action `confirm_email_code` + `EmailConfirmationCodeSerializer`) — authentifier après vérification réussie

C'est le **seul** moment où un utilisateur public reçoit ses tokens pour la première fois. Après `serializer.save()` (qui marque `email_confirmed=True` et consomme le code), générer les tokens JWT et créer une `MobileSession`, en suivant exactement le pattern déjà utilisé dans `activate_expert` ([views.py:56-84](api/v1/mobile/views.py#L56-L84)) :

```python
serializer = EmailConfirmationCodeSerializer(data=request.data)
serializer.is_valid(raise_exception=True)
user = serializer.save()

refresh = RefreshToken.for_user(user)

device_id = request.data.get('device_id', 'unknown')
device_type = request.data.get('device_type', 'android')
ip_address = self._get_client_ip(request)
user_agent = request.META.get('HTTP_USER_AGENT', '')

expires_at = timezone.now() + timedelta(days=30)
MobileSession.objects.create(
    user=user, device_id=device_id, device_type=device_type,
    ip_address=ip_address, user_agent=user_agent, expires_at=expires_at
)

return Response({
    'message': 'Email confirmé avec succès. Bienvenue !',
    'user': MobileUserDetailSerializer(user).data,
    'access': str(refresh.access_token),
    'refresh': str(refresh),
}, status=status.HTTP_200_OK)
```

`RefreshToken`, `MobileSession`, `timedelta`, `timezone` et `MobileUserDetailSerializer` sont déjà importés dans `views.py`.

### 4. `resend_confirmation_code` — déjà conforme

`EmailConfirmationCode.create_for_user` supprime déjà les codes non utilisés existants avant d'en créer un nouveau ([models.py](apps/mobileapp/models.py) `create_for_user`) → "l'ancien code est annulé" est déjà respecté. Aucun changement nécessaire ici.

### 5. `EmailConfirmationCodeSerializer` — pas de changement structurel

`validate()` vérifie déjà : utilisateur existe, email pas déjà confirmé, code actif existe, code valide (non expiré/non utilisé), code correct. `save()` marque `email_confirmed=True` et consomme le code. On garde cette logique telle quelle ; seule la **vue** ajoute l'émission des tokens après `save()`.

## Vérification end-to-end

1. Recharger le serveur (`python manage.py runserver`).
2. `POST /api/v1/mobile/auth/register_public/` avec un nouvel email → vérifier la réponse 201 **sans** champs `access`/`refresh`, avec `requires_email_confirmation: true`, et qu'un email avec un code à 6 chiffres part bien (log `tasks ... Code de confirmation envoyé à ...`).
3. `POST /api/v1/mobile/auth/login/` avec ce compte (avant confirmation) → vérifier réponse `403` avec `error_code: 'EMAIL_NOT_CONFIRMED'` et qu'un **nouveau** code est envoyé (et que l'ancien est bien supprimé en base — un seul `EmailConfirmationCode` non utilisé par utilisateur).
4. `POST /api/v1/mobile/auth/confirm-email-code/` avec un code erroné → erreur de validation, pas de tokens.
5. `POST /api/v1/mobile/auth/confirm-email-code/` avec le bon code → réponse 200 avec `access`/`refresh`/`user`, `email_confirmed=True` en base, et une `MobileSession` créée.
6. `POST /api/v1/mobile/auth/login/` avec ce compte désormais confirmé → connexion normale avec tokens.
7. `POST /api/v1/mobile/auth/resend-confirmation-code/` → vérifier qu'un nouveau code est généré et que l'ancien (`is_used=False`) est bien supprimé/remplacé.
